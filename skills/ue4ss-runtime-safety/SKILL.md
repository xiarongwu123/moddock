# UE4SS gameplay authoring

Read `references/runtime-contract.md` before writing UE4SS code, including revisions. Inspect the selected game, installed Mod evidence and loader capabilities. Verify each game-specific UFunction and its full signature with `search_api` or local SDK evidence. A static SDK match does not prove compatibility with this game build.

## Mandatory executable acceptance contract

For every new UE4SS Lua Mod, the host injects a lexical `ModdockVerification` API. Declare 1–12 distinct observable outcomes using `ModdockVerification.expect("lowercase_id", "observable behavior")`. Missing declarations or state readbacks fail the build and trigger automatic repair. Do not define, shadow or replace this API. REFramework Lua uses the same contract.

At the real feature trigger, call `ModdockVerification.begin("id")`. After the game has applied the change, on the correct thread reacquire live objects and call `ModdockVerification.check("id", actual, expected, tolerance)` with a number, boolean or string. The host compares values. `actual` must come from the effective game state, not a constant, a pcall result, a requested value, a local enabled flag or the same variable just written. Check again after the game's update so overridden writes fail. Numeric tolerance defaults to zero. Example: for a camera feature, read the effective view target/camera location after the camera update and compare to the intended position, not just the component property you assigned. Also verify restoration using a separate expectation. For physics read actual simulation state after the transition, not merely the attempted native call.

Wrap asynchronous feature entry callbacks with `ModdockVerification.guard("id", function(...) ... end)` so Lua failures reach the host. It is a Lua error reporter and does not prevent native crashes. Report incompatible required interfaces with `ModdockVerification.fail("id", "exact missing interface")`. Each begun check must finish within 15 seconds. Do not begin checks while waiting for a mission or an unused hotkey. Never log success on initialization alone, manufacture probe values or add native calls just to print diagnostics. If an effect has no reliable readback, identify the limitation; do not fake an executable contract.

`guard(id, fn)` RETURNS a wrapped function; it does not run `fn`. Register the returned function, for example `RegisterKeyBind(Key.F7, ModdockVerification.guard("helmet_enable", function() ExecuteInGameThread(ModdockVerification.guard("helmet_enable", toggle)) end))`. Alternatively call a stored wrapper or `ModdockVerification.guard("id", fn)(...)`. A bare guard call inside a callback silently does nothing and is a build error. Exercise the registered callback in a host simulation with a fake dispatcher before submitting; prove it reaches begin and a real-state reader, not just that registration succeeded. Report dispatcher/scheduling failure with fail instead of ignoring its return value.

The effective FOV reader belongs to `PlayerController.PlayerCameraManager:GetFOVAngle()`, with reflected path `/Script/Engine.PlayerCameraManager:GetFOVAngle`; do not invent `/Script/Engine.PlayerController:GetFOVAngle`. FOV widening/pulsing alone is not camera translation, angular bob, helmet placement or rotational lag. Preserve all promised mechanics and give each material outcome a corresponding effective-state assertion; if the required camera-pose interface is unresolved, report that limitation rather than describing a FOV-only implementation as full helmet-camera motion.

Runtime failures are fed back as `validation.runtime` (run ID, measured vs expected values, pending checks, process/fatal evidence and attribution uncertainty). Repair the actual behavior while preserving the user's request and meaningful assertions. Never remove assertions to make a failing feature pass. The host builds the repair, waits until the game is closed, deploys through the installation manager, relaunches and observes again, with at most two repair attempts. Only a new run can validate the repaired revision. A native crash observed in a multi-Mod run does not prove this Mod alone caused it.

When a property write succeeds but the effective state remains unchanged, investigate the actual owner of that state before choosing a repair. Matching a component's initial value to the current camera value does not establish that it drives the rendered view. Repeating the same write from a hook is only a hypothesis: verify that the hook executes for the live local player, and inspect any higher-level override or lock. Check inherited reflected entry points as well as game-specific functions. For Unreal FOV, the documented `APlayerController::FOV(float NewFOV)` is a candidate distinct from the non-reflected camera-manager setter; resolve and validate its UFunction in this build before using it. See https://dev.epicgames.com/documentation/en-us/unreal-engine/API/Runtime/Engine/APlayerController . This is not a claim that every Shipping build supports it. Do not change persistent game settings to evade a failed reversible camera feature. Keep both the real effective-state assertion and restoration assertion through every revision.

Observed local Ready or Not Steam build 25784851 on 2026-10-19: `PlayerCameraManager.SetFOV` was not reflected; both a camera-component FOV write and repeating that write after `CaptureFPCamera` still measured 90 instead of 110. A separately generated revision using the validated `PlayerController:FOV(float)` entry point measured 110 after the toggle and 90 after restoration, via delayed `GetFOVAngle` reads. Prefer investigating this proven entry point for this build over repeating those failed component-write hypotheses. Revalidate the interface and effective result on another build; this observation does not prove arbitrary camera features or other Mods safe.

Prefer the game's existing gameplay flow when it meets the request. Do not create a second camera, duplicate physics state or guess an alternate signature after an error. Preserve the user's requested mechanic; removing the feature, writing a log-only Mod or adding many `pcall` wrappers is not a crash fix.

Keep UObject work on the game thread. Use the installed loader's supported game-thread delayed APIs. Do not capture hook parameter wrappers across callbacks. Reacquire delayed targets and check the current mission and object identity before calling them. A non-nil UE4SS object can still be invalid; require `IsValid()` for lookup results.

Before `submit_result`, write the actual source, call `validate_project`, read every diagnostic and revise the source. Host risk diagnostics identify a rule, source line and repair direction. A failing risk check is an implementation error to repair within the existing automatic repair budget, not a request for the user to edit code or inspect crash logs. When a necessary interface cannot be verified, preserve the source and identify the exact blocker without calling the Mod playable.

For this implementation, check missing interfaces, rapid repeat input, death/arrest/respawn, a delayed callback after mission change, and overlap with installed Mods that modify the same subsystem. Use host simulation or game tests when available; do not invent their results. Distinguish syntax, static risk checks, simulated scenarios, loader initialization and actual gameplay verification. None alone means “zero risk” or “never crashes.”
